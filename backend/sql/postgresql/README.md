# Traducción del script MySQL a PostgreSQL

Esta traducción conserva el modelo del script entregado por el usuario: 13 tablas, planes separados, repuesto asociado a una máquina y consumos internos del registro. Requiere PostgreSQL 15 o posterior y puede ejecutarse desde el SQL Editor de Supabase.

## Orden de ejecución

1. `01-esquema.sql`: tablas, índices, funciones, triggers, vista y restricciones de acceso.
2. `02-datos-prueba.sql`: opcional, únicamente en desarrollo y con las tablas vacías. Incluye empleados ficticios y PIN de ejemplo diferentes de los usados en la instalación original. No usar esas credenciales de ejemplo en producción.
3. `03-verificar.sql`: consultas de solo lectura; no muestran PIN.

Ejecutar los archivos completos, de a uno, como propietario de los objetos. Cada archivo tiene su transacción. Si se interrumpe una ejecución con `psql`, ejecutar `ROLLBACK` o cerrar esa conexión antes de reintentar.

El primer archivo crea objetos en `public`, sin borrar tablas existentes. Si ya existe una tabla Climatic, falla y revierte la instalación en vez de reemplazarla. No usa `CREATE DATABASE`, `USE`, `DROP SCHEMA ... CASCADE` ni modifica los esquemas `auth`/`storage` de Supabase. No es una migración sobre una instalación Climatic previa.

No ejecutar junto con `backend/src/db/migrations/001_auth.sql` ni con `docs/esquema-postgresql.sql`: corresponden a una propuesta anterior con un modelo diferente. Estos archivos nuevos tampoco se ejecutan desde `npm run db:migrate`.

## Equivalencias y diferencias explícitas

- `INT UNSIGNED AUTO_INCREMENT` → `BIGINT GENERATED BY DEFAULT AS IDENTITY`, limitado al máximo original 4294967295. Las FK usan BIGINT. La semilla reajusta todas las secuencias después de insertar IDs explícitos.
- `TINYINT(1)` → `BOOLEAN`; los ejemplos usan `TRUE`/`FALSE`.
- `DECIMAL` → `NUMERIC`, conservando precisión y escala. No se agregan restricciones empresariales que el original no tuviera.
- `ENUM` → `TEXT CHECK (...)`, conservando los valores y la posibilidad de NULL original.
- `DATETIME` → `TIMESTAMP(0) WITHOUT TIME ZONE`. Las fechas explícitas conservan su hora local; los valores automáticos usan `statement_timestamp()` convertido a `America/Argentina/Buenos_Aires`. Esto evita que el huso UTC de Supabase cambie la hora local almacenada y mantiene la hora de la sentencia, como en MySQL.
- Se conservan las acciones `ON UPDATE`/`ON DELETE` y los índices explícitos; se agrega el índice de `repuestos_proveedores.proveedor_id` que MySQL genera implícitamente para la FK.
- `<=>` → `IS NOT DISTINCT FROM`; para detectar cambios se usa `IS DISTINCT FROM`.
- Los triggers se escriben en PL/pgSQL. Los conflictos de compatibilidad/stock usan SQLSTATE `P0001`; las FK `23503` (o `23001` para RESTRICT en PostgreSQL 18), duplicados `23505` y CHECK `23514`. El adaptador Express los convierte a errores HTTP legibles.
- **Cascada y stock:** PostgreSQL ejecuta triggers de filas borradas por cascada, mientras que MySQL no. La función de devolución comprueba que siga existiendo el registro padre para conservar el comportamiento original: borrar directamente un detalle devuelve stock; borrar el padre con cascada no lo devuelve. La aplicación no permite borrar el historial.
- **Mayúsculas y acentos:** se usa la collation de PostgreSQL/Supabase. No equivale a `utf8mb4_unicode_ci`; por ejemplo, la unicidad de email puede distinguir mayúsculas donde MySQL no lo hacía. No se impone una normalización diferente sin acordarla.

La vista conserva exactamente la base de cálculo original: `MAX(medicion_horometro)` y `MAX(duracion_fin)` independientes, y horómetro actual más frecuencia cuando no hay registros. No se incorpora un calendario de primeros servicios ni una relación de ejecución extraordinaria.

El original no tiene triggers de actualización de consumos. Esta traducción tampoco agrega edición de consumos: no ejecutar UPDATE sobre cantidades, repuesto o registro de un detalle para corregir stock. La API actual no ofrece esa operación.

## Acceso en Supabase y producción

Las tablas tienen RLS habilitado sin políticas públicas y la vista usa `security_invoker`. Se revocan los permisos de estos objetos a PUBLIC y, si existen, a `anon` y `authenticated`. El SQL Editor como propietario puede administrar y cargar los datos. Los usuarios del login por PIN de Climatic no son usuarios de Supabase Auth; el frontend debe seguir accediendo a Express.

El esquema inicial conserva `empleados.pin CHAR(4)` y no incluye `sesiones`. Después de ejecutar estos scripts, seguí [la preparación del backend para Supabase](../../../docs/supabase.md): `npm run db:prepare-supabase` convierte los PIN a hashes y crea sesiones persistentes. El backend ya adapta las consultas, errores, BIGINT, NUMERIC y fechas locales a PostgreSQL. No vuelvas a ejecutar la semilla después de esa migración.

Los scripts de prueba no conectan a MySQL ni importan datos actuales. El SQL de ejemplo no es una copia de los datos que se fueron cargando desde la app.

## Prueba local aislada

En Windows, con PostgreSQL instalado, desde la raíz del repositorio:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File backend/scripts/check-postgres-translation.ps1
```

Por defecto usa los binarios de PostgreSQL 18 en `C:\Program Files\PostgreSQL\18\bin`; se puede indicar otra instalación con `-PostgresBin`. Crea un clúster temporal en un puerto libre de `127.0.0.1`, sin leer `.env` ni `.env.local`, y lo detiene y elimina al terminar. Requiere las dependencias ya instaladas en `backend` (`pg`). El acceso trust se limita a esa instancia local efímera para pruebas.

Comprueba creación, semilla, secuencias, restricciones, permisos de los roles Supabase simulados, bajas/cierres, horómetro, compatibilidad, stock, devolución de detalles, cascadas, rollback de un registro incompleto y consumo concurrente desde dos conexiones. A continuación prueba la migración de autenticación, preservación de ceros iniciales, sesiones persistentes y recorridos HTTP completos del backend.
